## System Overview

The complete RAG system has two files:

| File | Purpose |
|------|---------|
| `rag_system.py` | Core logic: indexing, embedding, search, Q&A |
| `rag_server.py` | MCP server: exposes RAG as tools for Claude Desktop |

Plus a documents folder:

```
~/ai-finance-tools/
├── documents/
│   ├── AAPL-10K.txt              # Source document
│   └── AAPL-10K-index.json       # Generated index with embeddings
├── rag_system.py                  # Core RAG logic
├── rag_server.py                  # MCP server
└── server.py                      # Week 1-2 watchlist server
```

## How the Index File Works

The index JSON file stores everything needed for search:

```json
{
  "document": "AAPL-10K.txt",
  "indexed_at": "2026-03-15T14:30:00Z",
  "model": "nomic-embed-text",
  "sections": [
    {
      "id": 0,
      "title": "Item 1: Business — Overview",
      "text": "Apple Inc. designs, manufactures, and markets smartphones...",
      "char_count": 4250,
      "embedding": [0.023, -0.041, 0.018, ...]
    },
    {
      "id": 1,
      "title": "Item 1: Business — Products and Services",
      "text": "iPhone. iPhone is the Company's line of smartphones...",
      "char_count": 3100,
      "embedding": [0.015, -0.033, 0.042, ...]
    }
  ]
}
```

Key points:
- **Section titles are preserved.** Each chunk knows which part of the
  document it came from.
- **Embeddings are stored.** You don't re-compute them every time you
  search — the index is generated once and reused.
- **The file is self-describing.** It records which model was used and
  when it was created, so you know if you need to re-index.

## MCP Tool: `search_document(query, doc_name)`

**What it returns:**

```json
{
  "query": "What are Apple's main risk factors?",
  "document": "AAPL-10K",
  "results": [
    {
      "section_title": "Item 1A: Risk Factors — Macroeconomic and Industry Risks",
      "excerpt": "The Company's operations and performance depend significantly on worldwide economic conditions and their impact on levels of consumer spending...",
      "similarity_score": 0.84,
      "confidence": "high",
      "section_id": 5
    },
    {
      "section_title": "Item 1A: Risk Factors — Legal and Regulatory Compliance",
      "excerpt": "The Company is subject to complex and changing laws and regulations worldwide...",
      "similarity_score": 0.79,
      "confidence": "high",
      "section_id": 6
    },
    {
      "section_title": "Item 1A: Risk Factors — Technology and Product Risks",
      "excerpt": "The Company's products and services may be affected by the introduction of new technologies...",
      "similarity_score": 0.76,
      "confidence": "high",
      "section_id": 7
    }
  ],
  "result_count": 3,
  "data_source": "local_ollama",
  "as_of": "2026-03-15T14:35:00Z"
}
```

**Key design decisions:**

- **Confidence labels** (high/medium/low) help the AI prioritize results.
  Only high and medium confidence results are used for Q&A.
- **Excerpts, not full text.** The search tool returns the first ~200
  characters. The full text is sent to the LLM in `ask_document`.
- **Section IDs** let you drill deeper: "Show me the full text of
  section 5" (though this is optional).

## MCP Tool: `ask_document(question, doc_name)`

**What it returns:**

```json
{
  "question": "What are Apple's main risk factors related to AI?",
  "document": "AAPL-10K",
  "answer": "According to Item 1A (Risk Factors — Technology and Product Risks), Apple identifies several AI-related risks: the company's products may be affected by rapid technological changes including AI, and the company faces competition from other companies investing heavily in AI capabilities. The filing also notes under Legal and Regulatory Compliance that evolving AI regulations across different jurisdictions could impact the company's operations.",
  "citations": [
    {
      "section_title": "Item 1A: Risk Factors — Technology and Product Risks",
      "section_id": 7,
      "relevance": "high"
    },
    {
      "section_title": "Item 1A: Risk Factors — Legal and Regulatory Compliance",
      "section_id": 6,
      "relevance": "medium"
    }
  ],
  "model_used": "qwen3.5:4b",
  "data_source": "local_ollama",
  "as_of": "2026-03-15T14:35:00Z",
  "note": "Answer generated by local model from indexed document sections. No data sent to cloud services."
}
```

**Key design decisions:**

- **Citations are structured.** Each claim links to a specific section.
  This is essential for investment research — you need to verify what
  the AI says.
- **Model disclosure.** The return tells you which model generated the
  answer. Your local model (whether 0.8b, 2b, 4b, or 9b) is less capable
  than Claude — the answer quality reflects this. That's by design:
  the local model retrieves, Claude reasons.
- **Privacy note.** The explicit note that no data left the machine is
  important for compliance-conscious organizations.

## MCP Tool: `get_rag_guide()`

```json
{
  "overview": "Local document Q&A system using Ollama. All document processing happens on this machine — no data is sent to cloud services.",
  "tools": {
    "index_document": "Index a new document. Provide the file path. Takes 1-3 minutes for a full 10-K filing. Only needs to be done once per document.",
    "list_documents": "See all indexed documents with section counts and index dates.",
    "search_document": "Search a document for relevant sections. Returns top matches with similarity scores. Good for browsing — shows where information lives.",
    "ask_document": "Ask a question about a document. Searches for relevant sections and generates a cited answer using the local LLM. Good for specific questions."
  },
  "recommended_flow": [
    "1. index_document(file_path) — index the document (one-time)",
    "2. list_documents() — verify it was indexed successfully",
    "3. search_document(query, doc_name) — browse for relevant sections",
    "4. ask_document(question, doc_name) — get a cited answer"
  ],
  "important_notes": [
    "All processing uses local Ollama models — no cloud APIs involved",
    "Answers are generated by a local model which is less capable than Claude. Use these answers as starting points and verify important claims.",
    "Citations reference specific document sections — always check the source",
    "If Ollama is not running, tools will return an error with instructions to start it"
  ]
}
```

**The honesty note matters.** The guide tells the AI that local model
answers are "less capable than Claude" and should be used as "starting
points." This prevents Claude Desktop from presenting a local model's
rough answer as a definitive analysis.

## The Hybrid Pattern in Action

Here's what happens when you ask Claude Desktop "What does Apple's 10-K
say about AI risk, and how is AAPL doing today?":

```
1. Claude calls ask_document("AI risk", "AAPL-10K")
   → Your RAG server searches locally via Ollama
   → Returns cited passages about AI risk (local, private)

2. Claude calls get_stock_snapshot("AAPL")
   → Your Week 1 server fetches live data via yfinance
   → Returns current price and daily change (cloud API)

3. Claude synthesizes both:
   "Apple's 10-K identifies AI regulation as a key risk factor
   (Item 1A). Meanwhile, AAPL is up 0.85% today at $195.20,
   suggesting the market isn't currently pricing in significant
   AI regulatory risk."
```

The document search was completely local. The stock data came from a
free cloud API. Claude's reasoning tied them together. This is the
practical hybrid approach — privacy where it matters, cloud capabilities
where they add value.

## Performance Expectations

Speeds vary by model size and machine. These are rough guidelines:

| Operation | 0.8b (8GB machine) | 4b (16GB machine) | 9b (32GB machine) |
|-----------|--------------------|--------------------|--------------------|
| First call (model loads) | 2-5 sec | 5-10 sec | 10-20 sec |
| Embedding one section | < 1 sec | < 1 sec | < 1 sec |
| Full 10-K indexing (~25 sections) | 1-2 min | 1-3 min | 1-3 min |
| Search query | < 1 sec | < 1 sec | < 1 sec |
| Q&A answer generation | 3-8 sec | 5-15 sec | 10-30 sec |

The first call is slow because Ollama loads the model into RAM. Subsequent
calls are fast. Indexing speed is mostly determined by the embedding model
(same across all setups). Answer generation is where the text model size
matters most — larger models are slower but produce better answers.

If performance is poor, check that other heavy apps aren't competing for
RAM, or drop to the next smaller model.
