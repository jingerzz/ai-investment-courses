Structured Data In, Reasoned Analysis Out

The tool-use pattern from Week 1 gives Claude access to structured data. But Week 2 is about the next step: how to design tools and prompts so that Claude synthesizes multiple data sources into coherent, reasoned analysis. This is where AI truly adds value in investment management.

The Synthesis Pattern

Instead of asking Claude to analyze one dataset at a time, you ask it to cross-reference multiple tools in a single reasoning pass. Here's the pattern:

def get_current_signal():
    """
    Returns today's trading signal from the strategy framework.
    Combines market color classification, signal tier, exposure target.
    """
    return {
        "signal_name": "T1_BOTH_STRONG_BLUE",
        "signal_tier": 1,
        "color": "Blue",
        "exposure_target": 2.0,
        "as_of_date": "2025-03-07"
    }

def get_es_levels():
    """
    Returns ES futures pivot points, VWAP, and regime classification.
    Anchors directional trading levels.
    """
    return {
        "pivot": 5125.50,
        "s1": 5110.25,
        "r1": 5140.75,
        "vwap": 5132.10,
        "regime": "bull"
    }

def get_risk_report(account_size: int):
    """
    Synthesizes signal + levels to produce position sizing and trade plans.
    This is the output Claude should reason about.
    """
    return {
        "signal": "T1_BOTH_STRONG_BLUE",
        "long_plan": { "entry": "5115-5120", "stop": 5105, "target_1": 5140 },
        "contracts": 2,
        "total_risk_usd": 500
    }

When Claude sees a user question like "What should I do in ES today?", it can call these tools in sequence and synthesize the result:

  1. Call get_current_signal() to understand the market signal
  2. Call get_es_levels() to get current technical context
  3. Call get_risk_report() to get the complete trade plan
  4. Synthesize: "Here's today's signal (Tier 1 Blue), ES is at VWAP with bullish regime, and the trade plan is..."

The key: you don't make Claude do the math. All three tools return pre-computed, decision-ready information. Claude's job is to understand the narrative — why this signal matters, what the technicals support, when to execute.

Why This Beats Dashboards

A static dashboard shows you numbers. Claude can do something dashboards can't: cross-reference multiple signals and explain them in natural language.

Dashboard approach:
  • You see: Signal = Blue, ES Pivot = 5125.50, Regime = Bull
  • You have to synthesize: "These all align, so I should go long"
  • If something's wrong, you have to figure out why
AI reasoning approach:
  • Claude sees the same data and explains it: "Signal is Tier 1 Blue, meaning strong risk-on. ES is trading at VWAP with confirmation above the 50-day SMA. Regime is bull. All three align."
  • Claude flags misalignments: "Signal says Blue, but ES just broke below VWAP. Caution."
  • Claude suggests follow-ups: "Before entering, check duration of this Blue streak to assess risk."

RAG for Financial Documents

Retrieval-Augmented Generation (RAG) is how you let Claude reason about financial documents: 10-Ks, earnings transcripts, SEC filings. But standard RAG fails for structured finance docs. Here's why.

The Problem with Standard RAG

Vector-based RAG (the most common approach) has a critical weakness for structured financial documents:

  1. Chunking destroys hierarchy: A 10-K is a tree (chapters, sections, subsections). Vector RAG chunks it into flat pieces, losing structure.
  2. Summaries hide nuance: A vector DB stores summaries to save space. But finance docs need precise quotes, exact figures, exact dates.
  3. Context mismatch: You ask "What are the company's risk factors?" Vector RAG returns 5 loosely relevant chunks. The real Risk Factors section is buried.
  4. Cross-section reasoning fails: Questions like "How did this risk factor change from last year?" require comparing multiple sections. Vector RAG gives you fragments.
  5. No audit trail: When Claude cites a fact, can you verify it came from the document? Vector RAG makes this hard.

Structure-First RAG (PageIndex)

Structure-First RAG (also called PageIndex) inverts the problem: instead of summarizing and vectorizing, you preserve the document's hierarchy and let Claude navigate it.

Here's a 10-K tree structure:

10-K
├── Item 1: Business
│   ├── Overview
│   ├── Products & Services
│   └── Market Position
├── Item 1A: Risk Factors
│   ├── Market Risk
│   ├── Regulatory Risk
│   └── Technology Risk
├── Item 7: Management's Discussion & Analysis
│   ├── Results of Operations
│   ├── Liquidity & Capital Resources
│   └── Segment Performance
└── Item 8: Financial Statements
    ├── Consolidated Balance Sheet
    ├── Consolidated Income Statement
    └── Footnotes

Instead of summarizing the Risk Factors section, you give Claude access to the tree. Claude can:

  1. Ask: "What are the top risk factors?"
  2. Claude calls: get_document_section(doc_id, node_id="Item1A")
  3. You return: The complete, raw text of Item 1A
  4. Claude reasons over the actual text, not a summary

The critical rule: summaries are for navigation only. Answers must come from raw text. Your tools describe the structure (tree view, summaries). But when Claude needs to reason, it gets the full section.

Vector RAG vs Structure-First vs Hybrid

Approach Best For Accuracy Audit Trail Cost
Vector RAG General Q&A, blog posts Moderate (fuzzy matches) Poor (chunk IDs) Low (pre-embedded)
Structure-First Finance, legal, structured docs High (exact sections) Excellent (doc_id + node_id) Medium (fetches on demand)
Hybrid Mixed: some navigation, some search High (best of both) Good (with metadata) Medium-High

For finance, Structure-First is the standard. PageIndex (a Structure-First system) achieved 98.7% accuracy on FinanceBench, a benchmark of finance document Q&A. Vector RAG scored 75%.

Where AI Reasoning Adds Value (and Where It Doesn't)

AI is powerful but not magic. It excels at certain tasks and fails at others. Understanding this boundary is critical for building reliable financial AI.

High-Value Tasks for AI

Cross-signal synthesis: "Here's SPY/TLT signal, ES technicals, and bond correlation. What does it mean?" Claude excels at this narrative reasoning.
Natural language trade plans: Instead of a grid of numbers, Claude can say: "Tier 1 Blue signal with bullish ES regime. Buy dip to S1 (5110), stop 5105, target 5140. Conviction: High."
Pattern explanation: "You've seen 3 consecutive Red days. Historically, the next day averages a 0.5% bounce. That's mean reversion."
Document Q&A: "What were the company's main risk factors last year vs this year?" Claude reads the raw 10-K sections and compares.
Anomaly narration: "This position is down 15% vs 2% benchmark loss. Unusual. Let me check if there's a specific event..." Claude can reason about outliers.

Low-Value (Keep in Python)

Numerical computation: Portfolio Greeks, VaR, correlations. Python is faster and exact. Don't make Claude calculate.
Precise pricing: Option valuations, bond yields, spreads. Claude will hallucinate. Use your pricing library.
Backtesting: Historical performance, returns distribution. Claude can't run backtest logic. Compute it in Python.
Order execution: Actually placing trades. Too risky. Claude generates orders, your system executes them after approval.

The Pre-Formatted Template Pattern

The best way to separate AI reasoning from computation is the pre-formatted template pattern. Instead of giving Claude raw numbers to assemble, you give it a formatted briefing:

def get_trade_briefing(symbol: str = "ES"):
    """
    Returns a pre-formatted, ready-to-display morning briefing.
    All numbers are pre-computed. Claude reads and reasons about it.
    """
    return {
        "briefing": """
MARKET BRIEFING — March 7, 2025 — ES Futures

STRATEGY SIGNAL: Tier 1 Blue
Conviction: HIGH | Exposure: 2.0x

ES TECHNICALS
Current: 5127.50 | Pivot: 5125.50 | VWAP: 5132.10
Regime: Bull (above SMA50=5100, above SMA200=5080)
Yesterday: Close 5130, High 5145, Low 5120

TRADE PLAN: LONG
Entry: 5115-5120 (dip toward S1)
Stop: 5105 (12.5 pts = $625/contract)
Target 1: 5140 (R1, +25 pts = $1250)
Target 2: 5155 (R2, +40 pts = $2000)
Risk/Reward: 1:2

POSITIONING
2 ES contracts | 500 USD at risk | R:R = 1:2
        """,
        "as_of_date": "2025-03-07 08:30 ET",
        "stale_warning": None
    }

Claude sees this formatted briefing and can reason about it: "Signal is strong, technicals align, risk/reward is good. Proceed." It's not calculating; it's interpreting and explaining.

Prompt Engineering for Financial AI

The art of getting Claude to reason well about finance comes down to two factors: tool docstrings and return field names. These act as implicit prompts.

Tool Docstrings Are Prompts

When you write a tool docstring, Claude reads it before deciding whether to call the tool. A weak docstring confuses Claude. A strong one guides it.

Weak Docstring
def get_data(ticker):
    """Get market data."""

Claude doesn't know what "market data" means. Is it price? Volume? Fundamentals?

Strong Docstring
def get_equity_snapshot(ticker: str):
    """
    Fetch live price, technicals, and context for a US stock or ETF.

    Returns: last price, bid/ask, 52-week high/low, SMA50, SMA200, ATR14,
    pivots (P, R1-R3, S1-S3), and regime classification (bull/bear).

    Use this when you need to: assess current valuation vs levels,
    check technical regime, size a trade entry/stop.
    """

Claude knows exactly what this tool returns and when to use it.

Return Field Names Are Prompts

How you name fields in the return value teaches Claude what to focus on.

Weak Return Fields
return {
    "v1": 5125.50,
    "v2": 5110.25,
    "v3": 5140.75,
    "v4": "bull"
}

Claude has no idea what v1, v2, v3 are. It can't reason about them.

Strong Return Fields
return {
    "pivot": 5125.50,
    "support_1": 5110.25,
    "resistance_1": 5140.75,
    "regime": "bull",
    "context": "Price at VWAP, above SMA50, strong uptrend."
}

Now Claude immediately understands: these are price levels, regime, and context. It can reason about them.

Key Takeaways

  1. The synthesis pattern lets Claude cross-reference multiple tools to produce reasoned analysis, not just aggregated data.
  2. Structure-First RAG (PageIndex) preserves document hierarchy and gives Claude access to raw text for accurate reasoning.
  3. Vector RAG fails for finance docs because it flattens hierarchy and returns summaries instead of exact sections.
  4. AI reasoning adds value for narrative synthesis, trade planning, pattern explanation, and document Q&A.
  5. Keep numerical computation, pricing, backtesting, and order execution in Python, not Claude.
  6. Pre-formatted templates separate computation from reasoning, letting Claude focus on interpretation.
  7. Tool docstrings and return field names act as implicit prompts, shaping how Claude reasons about your data.

Build a Morning Briefing with Guardrails

This exercise walks you through adding market context tools and building a pre-formatted morning briefing. By the end, you'll have a system that synthesizes multiple data sources with built-in guardrails.

Open Your Project
1 minute

Start Claude Code on your Week 1 MCP server:

$ cd my-first-mcp
$ claude code .

You should see your existing MCP server with portfolio tools ready to extend.

Add Market Context Tools
8 minutes

Ask Claude Code to add three new tools for market-wide context:

Prompt
Add three market context tools to my MCP server:

1. get_market_overview() — returns SPY price, market regime (bull/bear), VIX, market breadth (advance/decline ratio)

2. get_sector_heatmap() — returns performance and strength for each major sector (Tech, Financials, Healthcare, etc.). Include relative strength vs SPY.

3. get_watchlist_movers() — returns top 5 gainers and losers among a predefined watchlist (include AAPL, MSFT, NVDA, TSLA, GLD, SHV)

Each tool should return:
- Pre-computed, decision-ready values (not raw data)
- Metadata: as_of_date, data_source, stale_warning
- Clear field names so Claude understands what each value means

Make sure they integrate with your existing portfolio tools.

Claude Code will extend your server with these tools. Test them with the MCP Inspector to verify they return properly structured data.

Add Pre-Formatted Briefing Tool
7 minutes

Now ask Claude Code to build the star tool — the pre-formatted briefing:

Prompt
Add a get_morning_briefing() tool that synthesizes everything:

Return a dictionary with a "briefing" field containing a pre-formatted markdown briefing like:

MORNING BRIEFING — [DATE] — [TIME]

MARKET REGIME
SPY: [price] ([change]%) | Regime: [bull/bear] | VIX: [value]

SECTOR STRENGTH
[Top 2 sectors by performance]
[Bottom 2 sectors]

PORTFOLIO CONTEXT
Your portfolio exposure to top sectors
Risk posture vs market breadth

WATCHLIST MOVERS
Top 3 gainers (with % change)
Top 3 losers (with % change)

Also return: as_of_date, data_source, stale_warning

This tool should call your market context tools internally and format everything nicely. Claude will read this briefing and reason about what to do.

Once built, test it. Call get_morning_briefing() and verify the output is readable and well-formatted.

Update the Guide Tool
3 minutes

Update your guide tool to include the new market context and briefing tools:

Prompt
Update the get_portfolio_tools_guide() tool. Add sections for:
- Market context tools (market_overview, sector_heatmap, watchlist_movers)
- Briefing tools (morning_briefing)

For each tool, include:
- Name
- What it returns
- When Claude should use it

Example format:
"market_context": [
  {
    "name": "get_market_overview",
    "returns": "SPY price, regime, VIX, breadth",
    "when": "Need to assess overall market health before making portfolio decisions"
  }
]

Test the guide tool to make sure it's clear and useful.

Test the Briefing in Claude Desktop
6 minutes

Now test your complete system in Claude Desktop:

  1. Restart Claude Desktop to load your updated server
  2. Start a new conversation
  3. Ask: "Give me a morning briefing and tell me if we should rebalance our tech exposure"

Claude should call get_morning_briefing(), synthesize the data, and give you a reasoned answer.

Now try these tricky prompts:

Tricky Prompt 1
"The briefing shows tech is down, but our portfolio is heavy tech. Should we hedge?"
Tricky Prompt 2
"What if the VIX spiked 50% overnight? How would that change your recommendation?"
Tricky Prompt 3
"Compare our portfolio's sector exposure to the market heatmap. Where are we overweight and underweight?"

These prompts test whether Claude is truly synthesizing data or just echoing individual tool outputs.

Add Stale Data Warning
5 minutes

Ask Claude Code to add a guardrail for stale data:

Prompt
Add a guardrail: if any market context tool returns data older than 15 minutes, include a stale_warning in get_morning_briefing(). The warning should say:

"WARNING: Market data is [X minutes] old. Prices may have moved. Refresh before making trading decisions."

Also, if VIX shows data older than 1 minute, flag it specifically:
"WARNING: VIX data is stale. Volatility may have spiked. Check current levels before hedging."

This should be returned in the stale_warning field, and Claude will see it and mention it to the user.

Test this by manually setting old timestamps in your mock data and verifying the warning appears.

Prompt Patterns for Week 2

This section shows you how to talk to Claude about more complex synthesis and guardrails. These patterns build on Week 1.

Building on Existing Code

Good
You: "I have a get_portfolio_summary() tool from Week 1. Now add a get_market_sentiment() tool that returns VIX, put/call ratio, and breadth. Both should return as_of_date and stale_warning. Make sure stale_warning triggers if data is older than the market open time."
References existing code, specifies new tool clearly, explains the guardrail requirement (stale data warning for pre-market data).
Less effective
You: "Add more tools."
Claude doesn't know what tools, what they should return, or what guardrails to include.

Describing Guardrails

Guardrails are special logic that protects Claude from making bad decisions. Here's how to describe them:

Pre-Formatted Templates
All tools should return data in a consistent format. Use this template:

{
  "data": [...],
  "as_of_date": "ISO timestamp",
  "data_source": "where this came from",
  "stale_warning": "null or a warning message"
}

Claude will see stale_warning and mention it when talking to the user.
Stale Data Warnings
If data is older than [X minutes], return a stale_warning like:
"Market close was 4.5 hours ago. This data may be outdated. Refresh for current levels."

This helps Claude know not to make real-time trading decisions with EOD data.
No-Compute Rule
Tools should NOT:
- Calculate VaR or Greeks (too complex for tool return types)
- Place orders (too risky)
- Modify database state (only read)
- Return raw data (only decision-ready summaries)

If Claude asks "can this tool compute X?", the answer is: "No, X is computed in Python. The tool returns pre-computed X for Claude to reason about."

When AI Gets Something Wrong

Claude will sometimes hallucinate, ignore your formatted sections, or fail to cross-reference tools. Here's how to recover:

When Claude Makes Up Numbers
Claude: "Your VIX exposure jumped 200%."
You: "That's not right. Call get_market_overview() to get current VIX. What does it actually say?"

Claude will call the tool and see real data.
When Claude Ignores the Formatted Section
Claude: "I'll analyze your positions in detail." [ignores the pre-formatted briefing]
You: "Actually, I sent you a pre-formatted morning briefing. Please use that as your base and reason about it. Then explain if anything is missing."

Claude will re-read the briefing and reason properly.
When Claude Doesn't Cross-Reference
Claude: [calls get_portfolio_summary() but not get_market_overview()]
You: "Also check get_market_overview() — I want to know if our sector exposure aligns with market regime."

This teaches Claude to use multiple tools together.

Tips for Week 2

  • Field names matter: Use clear names like "pivot", "support_1", "regime". Avoid "v1", "x", "data". Claude reads field names as hints about what the values mean.
  • Always include context fields: as_of_date, data_source, stale_warning. These teach Claude to think about data freshness and provenance.
  • Test the guide tool first: If Claude isn't using new tools, the guide might not mention them clearly. Check that the guide explains when to use each tool.
  • Pre-format outputs for complex reasoning: Instead of returning raw numbers, structure them in markdown. Claude will reason better about formatted text.

Testing Methodology

Before considering Week 2 done, test these scenarios:

Ask a question that requires 2+ tools. Does Claude call them all?
Ask about a conflict (e.g., "Market is bullish, but our sector is down"). Does Claude reason about both?
Set stale data in a tool. Does Claude warn you before recommending action?
Ask Claude to explain a metric. Does it reference the tool it came from (audit trail)?
Common Issues & Fixes
  • Claude only calls one tool: Check guide tool. If it doesn't explain combinations, Claude won't use multiple tools.
  • Briefing format is messy: Use markdown with clear sections. Test output manually before hooking it to Claude.
  • Stale warnings don't appear: Verify the logic in get_morning_briefing(). Ensure stale_warning field is populated.
  • Claude ignores stale warnings: Include them prominently in the briefing text, not just in metadata. Claude reads the narrative.
  • Tools work but Claude won't call them: Docstrings are weak. Make them specific: instead of "Get data", say "Get current sector performance vs SPY to assess relative strength."
